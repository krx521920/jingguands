## 二、我做的 4 项对齐

| # | 契约要求 | 我原来的做法 | 现在的做法 |
| --- | --- | --- | --- |
| 1 | `provenance.region` | 字段名叫 `bbox` | **改名 `region`**，抽取层可直接 `prov["region"] = block["region"]`，零映射 |
| 2 | `quote` 必须是**原文子串** | 只有 `text`（跨行处会补空格，不是严格子串） | **新增 `text_raw`**，按阅读顺序直接拼接原始字符、不插入任何字符 |
| 3 | `source.file_id` 格式 `sha256:…` | 只有 `doc_id`（`d116fbfae`） | **新增 `file_id`** = `sha256:116fbfae…` |
| 4 | 需要填 `source` 对象 | 无 | **新增顶层 `handoff`**，把 `source` 预先拼好，可原样拷贝 |

另外补了一项契约没写的：**坐标语义**（见问题 2）。

### 为什么要单独加 `text_raw`（第 2 项）

真实公告里链接、邮箱常被换行拆开。`text` 为了可读性会在跨行处补一个空格，结果 **把链接拆断了**：

```
text     : '报名链接为:https://app.cufe .edu.cn/scenes/Aljc9u'   ← 多了一个空格
text_raw : '报名链接为:https://app.cufe.edu.cn/scenes/Aljc9u'    ← 连续原文
```

**如果抽取层拿 `text` 当 quote，`quote in 原文` 会直接失败。**

⚠️ **但要如实说明**：`附件1通知.pdf` 这份样例里 71 个块的 `text` 与 `text_raw` **恰好完全相同**，没有触发这个分叉。所以我专门写了一条构造用例（`test_text与text_raw在跨行西文处分叉`）来保证这个字段不是形同虚设。

### 抽取层怎么取（已在 `handoff` 里给出，不用猜）

```json
"provenance_from_block": {
  "block_id": "block.block_id",
  "page":     "block.page",
  "region":   "block.region",
  "quote":    "block.text_raw"      ← 注意是 text_raw，不是 text
}
```

## 三、发现的契约问题（3 项，请魏文宇确认）

### 🔴 问题 1：`parse_meta.blocks` 的 README 与 schema 自相矛盾（会导致校验失败）

**README 第四节说：**

> 张智博（解析/出处）：D2 起 `source.parse_meta` 由你填充（parser_version、page_count、**blocks**）

**但 schema 里 `parse_meta` 是这样定义的：**

```json
"parse_meta": {
  "type": ["object", "null"],
  "additionalProperties": false,
  "properties": {
    "parser_version": { "type": ["string", "null"] },
    "page_count":     { "type": ["integer", "null"], "minimum": 1 }
  }
}
```

`additionalProperties: false` ＋ 只允许两个字段 = **我要是真填了 `blocks`，抽取层一校验就挂。**

**我的处理**：按 schema 走，`parse_meta` 里**不放** `blocks`；块数据在 `pages[].blocks[]`；这个矛盾我写进了输出的 `handoff.warnings` 里，并加了一条回归用例锁住，不会静默踩坑。

**建议修法**（纯增量，不破坏任何已有校验）：

```json
"properties": {
  "parser_version": { "type": ["string", "null"] },
  "page_count":     { "type": ["integer", "null"], "minimum": 1 },
  "blocks":         { "type": ["array", "null"], "items": { "type": "object" } }
}
```

改完之后我就能把块直接塞进 `parse_meta`。**在你改之前我按现在的 schema 走。**

### 🔴 问题 2：`region` 没有声明坐标语义（会让高亮框整体偏移，而且不报错）

**schema 现在只写了：**

```json
"region": {
  "type": ["array", "null"], "items": { "type": "number" },
  "minItems": 4, "maxItems": 4,
  "description": "[x1,y1,x2,y2] 页面区域坐标（解析侧 D2+ 供给）"
}
```

**缺三样东西**：单位是什么（PDF 点？像素？毫米？）、原点在哪（左上？左下？）、顺序是什么（left/top/right/bottom？还是 x/y/w/h？）。

这不是小事：**陈家浩按错的原点渲染，高亮框会整体上下翻转或偏移，而且程序不会报任何错**——只是框画歪了。

**我的处理**：在输出的 `doc.coord_system` 里显式声明清楚：

```json
"coord_system": {
  "unit": "pdf_point",
  "unit_zh": "PDF 点（1 pt = 1/72 英寸）",
  "origin": "top_left",
  "origin_zh": "页面左上角，y 轴向下为正",
  "field": "region",
  "order": ["left", "top", "right", "bottom"],
  "normalize_hint": "屏幕坐标 = region / [page.width, page.height] × 显示尺寸"
}
```

**建议**：在契约侧补一行说明（哪怕只是把上面这段抄进 `region` 的 description），这样页面和评测两端都不用靠猜。

---

### 🟡 问题 3：`region` 写成 `[x1,y1,x2,y2]` 有歧义

`x1,y1,x2,y2` 容易被读成「两个点」或「x/y/宽/高」。我按 **`[left, top, right, bottom]`** 实现，并在 `coord_system.order` 里写死。建议契约里也用 `[left, top, right, bottom]` 这种自解释的写法。

## 四、给每个人的对接点

### 魏文宇（抽取/编排）

1. 上面三个问题，请在 `interface/` 里确认或修掉。**问题 1 建议今天就改**，是一行的事。
2. 我的输出已经备好东西了：读 `handoff.source` 可直接拷进信封；`handoff.provenance_from_block` 给出 `provenance` 四个字段的取法。
3. 提醒一个架构事实：**你的入口是 Node，我的解析是 Python**，所以只能通过 JSON 文件/stdout 交互。我的 CLI 已经输出干净 JSON（`python -m finstruct.parse.parse_pdf <pdf> -o <json>`）。
4. D1 阶段你的样例是 `.txt`、绕过了 PDF 解析；D2/D3 接进来时需要多一个 `--parse-json <file>` 之类的入口。这是你那边的事，只是提前说一声。

### 陈家浩（页面）

1. 高亮坐标取 `block.region`，**换算方式按 `doc.coord_system.normalize_hint`**：
   ```
   屏幕坐标 = region / [page.width, page.height] × 显示尺寸
   ```
2. **不要假设 A4 或固定页面尺寸**——`width`/`height` 每页都给了。
3. `role` 可直接用于样式：`TITLE`（大标题）/ `SECTION`（章节标题）/ `BODY` / `HEADER` / `FOOTER`。页眉页脚**保留在数据里**（可能承载日期等信息），只是不该当正文显示。
4. 证据展示时显示 `block.text`（可读），但**引用/复制给用户时用 `block.text_raw`**。

### 方轩诚（口径/标准化）

我的解析层只做**文本与坐标**，不碰数值口径——`raw_value` / `value` / `unit` 的标准化完全是你的事，我不越界。但有一处交界：**表格单元格的定位由我提供**（D3/D4 会填 `pages[].tables[].cells[]`，带 `table_id` / `row` / `col` / `region`）。你算比例时如果要标"这个数出自哪个单元格"，那时才需要我的 cell 级坐标。

### 宗博文（评测）

出处的评测可以分两层，我的输出刚好支持：

| 指标 | 判据 | 我的字段 |
| --- | --- | --- |
| **区域级出处命中** | 标注的区域与 `region` 是否重叠 | `block.region` + `page.width/height` |
| **单元格级出处命中** | `(table_id, row, col)` 是否一致 | `cells[].table_id/row/col` |
| **引文忠实性** | `quote` 是否是原文子串 | `block.text_raw`（我这边自测 71/71 = 100%） |

按团队指标要求，**区域级和单元格级要分开统计**——我的结构支持分开取。
