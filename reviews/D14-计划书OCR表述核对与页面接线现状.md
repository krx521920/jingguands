## 一、必须报的问题：计划书承诺了**没有的 OCR**

计划书里与扫描件相关的表述，逐条对照实现：

| 计划书原文 | 实现实际 | 判定 |
| --- | --- | --- |
| 「扫描件**先走本地 OCR**；无法可靠读取时标记为 unreadable」 | **无 OCR**。`scan.try_ocr` 存在但明确返回不可用；`OCR_CHANNEL_ID = "none"` | ❌ **与实现不符** |
| 「扫描件 OCR ／ **PP-OCRv5 / PaddleOCR 离线候选**」 | 未实现 | ⚠ 写的是"候选"，尚可，但列在能力表里易被读成已有 |
| 「表格结构可以使用 **MinerU 或 PP-Structure** 增强」 | 未实现 | ⚠ 同上，"可以…增强"是选项语气，边界模糊 |
| 风险缓解措施写「**本地 OCR 与区域截图并行**，低置信度交人工」 | 未实现 | ❌ **这是缓解措施，会被读成已具备的能力** |
| 「扫描件和无框表属于**辅助能力**」 | **与实现一致** ✓ | ✅ |

### 我的判定

**「先走本地 OCR」这一句必须改**，其余三处建议加限定词。

理由与本项目刚裁定的「双通道 6/14」是**同一条原则** ——
**每个数字/能力都要有 artifact 支撑**。魏的裁决书写得很清楚：

> 本项目立身原则是每个数字带分母＋出处 —— 无 artifact 支撑的数字不进任何材料、成绩、边界表述。

**OCR 能力当前没有 artifact。** 而这一句正好在「七、解析与可复现」的技术主张段里，
答辩时若被追问"OCR 用的什么模型、准确率多少"，我们没有答案。

### 建议改法（三选一，我推荐第 1 条）

**① 如实降级（推荐）**

> 解析层优先消费文本 PDF 或 finstruct 解析包，保留段落和表格单元格坐标。
> **扫描件当前只做降级**：标记 `unreadable` 并保留区域级证据，
> 不把解析失败写成"原文未提及"。**本地 OCR 为规划中的辅路，尚未实现**，
> 故涉及扫描件的字段一律进入证据不足，不参与数值比较。

**② 若坚持保留 OCR 承诺** —— 则必须**先做出 artifact**（哪怕是 PP-OCRv5 的离线试验），
并把它的命中**单独报分母**，不得混进解析命中率。

**③ 若已在别处实现**（例如页面侧的 `dual-channel`）—— 请指出**来源分支与产物**，
我按同样标准核。**我不认领也不否认，只认 artifact。**

### 一处已登记、无需改的

计划书说「表格解析失败时**保留区域级证据**」—— 与我登记的一致 ✓
（无框表格内容进正文流、`tables=0`，消费方按区域级处理）。

## 二、demo web 不是空壳 —— 是「接线完整、标牌写错」

### 实测：接线是通的

**13 个接口全在**：`datasets / engines / export / integration / metrics / metrics/registry /
pairs / parity / parity/real / result / upload / upload/log / verify`

**一次真实加载**（`wei_real_awd_001`）：

```
事件 1 / 证据 5 / 字段 14
证据字段：evidence_id, block_id, page, bbox, source_type, table_id, cell_ref, header_path
```

**注意最后四个** —— `block_id` / `bbox` / `cell_ref` / `header_path`
**正是我解析输出的结构**。也就是说：

> **解析层的东西已经在页面里了**，而且是字段级、单元格级的。

### 所以「像空壳」是四个标记问题，不是接线问题

| # | 表现 | 实情 |
| --- | --- | --- |
| 1 | 标题写「三栏骨架（**D1**）」 | 内容已是 D11/D12 时期 |
| 2 | 常驻横幅「**模拟数据**——不得计入真实成绩」 | `data_unified/` 里是**权威信封** |
| 3 | 四个视图默认「未加载」 | 需手动选数据集，无自动加载 |
| 4 | clone 后指标卡全 null | `data_unified/` **被 gitignore**（宗 D14 的 P0） |

**第 4 条我亲测过**：按 README 起服务，三张卡全 null，30 个数据集没有一份"入口径"。
补上 32 份权威信封后立刻正常。

### 要把「已实现的结构化提取」接进去，其实只有三件事

链路现状：

```
PDF ──(finstruct 解析)──▶ parse.json ──(魏 抽取器)──▶ 事件信封 ──▶ 页面
        张                   张的产物          魏                陈
```

**页面只消费最后一跳的信封，它不解析 PDF**（这是设计要求，不是缺陷）。
所以"接进去"不需要改代码，只需要：

1. **把信封放进 `data/` 或 `data_unified/`** → 刷新浏览器，下拉框自动多出来
2. **解掉 `data_unified/` 的 gitignore**，否则 clone 看不到
3. **改那三处文案**（标题的 D1、模拟数据横幅、视图名）

**第 1 条是零代码的** —— 页面本来就是"放进来就出现在下拉"的设计。
