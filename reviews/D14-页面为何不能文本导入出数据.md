# 为什么页面不能「文本导入 → 出数据」

> 核查人：张智博　日期：2026-10-13
> 结论：**不是坏了，是三层都没接通** —— 且页面其实已经预留了接口，只是没人填。

---

## 一、三层原因，逐层查证

### 第 1 层：上传入口本来就不是给 PDF 的

| 位置 | 原文 |
| --- | --- |
| 前端 | `<input type="file" id="fileInput" **accept=".json"** multiple hidden>` |
| 后端 | `if (!/\.json$/i.test(filename)) entry.error = "**仅接受 .json 信封文件**"` |

**这是刻意限制，不是 bug** —— 页面设计上只消费"事件信封"，不消费原始文件。

### 第 2 层：三个抽取引擎，只有第一个可用

页面 `server.js` 头部自己写明了（`bridge/extractor.js`，D12 预留入口）：

| 引擎 | 说明 | 实测状态 |
| --- | --- | --- |
| **`file`** | 读 `data/<case>.json` **预生成信封**（默认） | ✅ `available: true` |
| `cli` | 预留：spawn 魏文宇抽取 CLI —— `EXTRACT_CLI_CMD` ＋ `EXTRACT_CLI_PDF_DIR` | ❌ **未接通** |
| `http` | 预留：调魏文宇抽取服务 —— `EXTRACT_HTTP_URL` | ❌ 未接通 |

**`/api/engines` 的实测返回（关键三条）**：

```jsonc
"default_engine": "file",
{ "id": "file", "kind": "prebuilt",
  "caps": { "reruns_extraction": false, "needs_pdf": false,
            "same_file_as_peer": true,
            "label": "预生成信封（未重新抽取）" } },
{ "id": "cli", "kind": "live", "available": false,
  "reason": "入口未接通：EXTRACT_CLI_CMD（未设抽取命令）；
             EXTRACT_CLI_PDF_DIR（未设原始 PDF 目录 —— **页面侧目前没有 PDF**）" }
```

**这就是"看起来是空壳"的根本原因** ——
默认引擎 `file` 的自我描述就是「**预生成信封（未重新抽取）**」，`reruns_extraction: false`。

**页面从不运行抽取，它只是把已生成的信封读出来显示。**

### 第 3 层：连 `live` 引擎的开关都是关的

```js
live_ready:              engines.some(e => e.kind === "live" && e.available)   // → false
can_rerun_extraction:    engines.some(e => e.kind === "live" && e.available)   // → false
```

`server.js:826` 还有一句：`if (!engines.some(e => e.kind === "live" && e.available))` ——
**没接通 live 引擎时直接走另一条分支**。

## 二、要接通，缺的是这四件（都不是"写代码"那么笼统）

| # | 缺什么 | 归谁 | 说明 |
| --- | --- | --- | --- |
| 1 | **可被页面调用的抽取 CLI** | 魏 | 设 `EXTRACT_CLI_CMD`：吃一个 PDF，吐一个事件信封 |
| 2 | **页面侧的 PDF 目录** | 陈/团队 | 设 `EXTRACT_CLI_PDF_DIR`；**注意引擎自己报的原因是"页面侧目前没有 PDF"** |
| 3 | **前端放行 PDF** | 陈 | `accept=".json"` → 加 `.pdf`；后端的 `仅接受 .json` 要同步放开 |
| 4 | **模型调用的处置** | 魏 | CLI 要吃模型服务。**要么真调（需密钥），要么给 mock/离线重放模式** —— 否则现场没网就演示不了 |

**注意第 1 条的措辞**：页面预留的是「**魏文宇抽取 CLI**」，
也就是说**架构假定 `PDF → 信封` 由魏的 CLI 一步完成**。

**我的解析（PDF → parse.json）在这条链里没有独立入口** ——
它被包在魏的 CLI 内部（他 vendor 我的解析产物到 `corpus/`）。
**所以第 1 条要接通，魏的 CLI 必须同时带上我的解析步骤**，
否则页面拿得到 PDF 也产不出信封。

## 三、如果只想做「解析可视化」（不需要模型，我能做）

**这是成本最低、且完全离线的一条路**：
上传 PDF → **只跑我的解析** → 页面展示块 / 表格 / 单元格 / 出处，不跑抽取。

| 项 | 情况 |
| --- | --- |
| 需要模型吗 | **不需要** —— 解析是纯本地计算 |
| 需要网络吗 | 不需要（渲染页面用的 PDFium 已在依赖里） |
| 谁做 | 解析侧（我）＋ 页面侧各一半 |
| 能展示什么 | 页数/形态（TEXT/SCANNED/MIXED）、块的 `block_id`/`page`/`region`、表格 `n_rows×n_cols`、单元格 `cell_ref`/`header_path`、**降级演示**（扫描页 `scan_region`、无框表 `tables=0`） |
| 成本 | 我的解析是 CLI（`python -m finstruct.parse.parse_pdf`），页面 spawn 一下即可；前端加一个 `.pdf` 分支 |

**代价说清**：这会**移动封版点**（改页面代码），与魏选定的**方案 A（不并入、不动树）冲突**。
所以要么单独立项、要么等封版之后再动。

## 四、我的建议

**不建议现在改。** 理由：

1. 方案 A 已裁定不动交付树；改页面就要重跑五道门 ＋ 魏复检
2. 第 1/4 条（魏的可调用 CLI ＋ 模型处置）**不在我手上**，页面改完也跑不通全链
3. **现场演示可以用现成路径**：`file` 引擎 ＋ `data_unified/` 32 份权威信封，
   加上 CLI（`python -m finstruct.parse.parse_pdf` ＋ 魏的 `run_extract.mjs`）**在终端演示全链** ——
   效果等价，零改动风险

**若赛题明确要求「网页内可上传原始文件并出结果」**，那就必须走上面四件，
**且要有人统一协调（魏的 CLI ＋ 陈的前端 ＋ 我的解析入口），不是某一方能单独完成的。**
