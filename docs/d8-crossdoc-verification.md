- **关联判定**（只用信封字段，不依赖原文——与封存 raw/gold 哈希锁定兼容）：
  - S1 实体重叠：主体名跨文档匹配（名称形态容差：全称/简称互含或子序列）
  - S2 数值锚点：≥6 位且非圆整（%10000≠0，排除总股本类）的股数/金额在两文档同时出现
  - S3 反向咬合：共享锚点中，一侧出自 increase 事件、另一侧出自 decrease 事件（转让双方文件：受让方增持额＝出让方减持额）
  - 判定：`(E≥2∧A≥1)∨(E≥1∧A≥2)∨(A≥1∧反向咬合)`
- **一致性核验**（仅相关组，事件对齐后逐字段）：
  - corroboration：同主体同字段跨文档数值一致（互证）
  - **合计勾稽**：群体合计事件的总量 = 对侧分人事件之和（跨档核验，不拆记到个人头上）
  - conflict：同主体同字段数值冲突（双方 quote 存证）
  - complementary：主体仅见于一侧 / 对侧仅覆盖部分成员（**部分覆盖不判矛盾**——如 002 只披露四名转让方中的两名一致行动人）

## 三、语义要点（为什么这样设计）

1. **合计事件不拆记个人**：003 的四人合计事件若把 8,427,900 记到每个人头上，会与 001/002 的分人值产生 6 条伪矛盾；正确语义是合计↔分人**之和**勾稽。
2. **部分覆盖非矛盾**：002 按口径只披露两名一致行动人，与 003 的四人合计只构成互补信息。
3. **非圆整过滤**：总股本类整亿/整万数（86,000,000 等）在无关文档间可能巧合相等，`%10000≠0` 排除。
4. **质押/中标无 increase/decrease 方向**：反向咬合天然不触发，跨类型无关组零误报的另一重保障。
