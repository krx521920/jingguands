## 二、文件唯一标识（D6 明确要求的一项）

- **`doc_id`**：由**内容哈希**派生（`d` + sha256 前 8 位），不用文件名。
  实测与宗博文 manifest 里预留的 10 个 `document_id` **逐一一致**。
- **`file_id`**：`sha256:<完整摘要>`。
- **`block_id`**：`{doc_id}_p{页码}_b{序号}`，带 doc_id 前缀。

**这三者合起来就是「跨文件出处串联」的答案**：批次里放多份文件时，
每份的 `doc_id` 不同、`block_id` 因此全局唯一，出处不会互相串。
`table_id` / `cell_id` 同样带 `doc_id` 前缀。

## 六、已知边界

1. **`D6-AWD-005` 的表格没有 `header_path` 是设计如此，不是漏检。**
   该表是 **7 行 × 2 列的竖排键值表**（`公司名称 / 统一社会信用代码 / 成立时间 / 住所 /
   法定代表人 / 注册资本 / 经营范围`），不是带表头的横表。
   解析层对 **`n_cols < 3`** 的表**一律不判表头行** —— 理由写在该函数里：
   窄表多半是「字段名: 值」的键值表，按网格表头处理会把每一行都误当表头。

   **正确的读法是按键值对，不是按列序：**

   | 位置 | 含义 |
   | --- | --- |
   | `col = 0` | **字段名**（键），就在格子里，不需要外部映射 |
   | `col = 1` | **字段值** |

   消费方判别规则：`n_cols < 3` → 键值表（按行读 键=col0、值=col1）；
   `n_cols >= 3` → 网格表（按 `header_path`）。
   两列表按键值对读是安全的 —— 即便它是「项目 | 金额」这类两列横表，
   读法同样成立。
2. 其余同 `sample/D5/README.md` 的已知边界（续表只打标不拼接、无框表格检不出、
  扫描件只降级不识别等）。
