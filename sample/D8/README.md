## 一、这个索引做与不做的事

**做**：从解析输出建立四类索引，**每个索引键都带块级出处**（`block_id` + `quote`）：

| 索引 | 键 | 用途 |
| --- | --- | --- |
| 文件索引 | `doc_id` / `file_id` / 页数 / 形态 | 文件唯一标识、批次可追溯 |
| 主体索引 | 正文中出现的公司名 | 检索「某名出现在哪些文件的哪些块」 |
| **发行主体索引** | **证券/股票代码**（回退标题公司名） | 同一发行主体的多份公告 |
| 日期索引 | 正文中出现的日期候选（**未筛**） | 检索 |
| **版本索引** | 发行主体键 → 按公告编号排序的版本链 | 公告版本引用 |

**不做**：**不判定「两份公告是否同一事件」。** 那是 B 流程的语义裁决
（同公司 ≠ 同事件）。本索引只保证「给出索引键时能指回它出现在哪个文件的哪个块」——
即「跨文件双侧出处」所需的那一半。

## 二、几个设计决定及其依据（都是实测逼出来的）

### 1. 发行主体键用**证券代码**，不用公司名

实测按公司名匹配会失败：

- `D5-EQC-003` 是《财务顾问核查意见》，**首块是财务顾问国海证券**，不是发行主体
- 同一主体在不同文档里的写法可能不同（简式/详式、有无地名前缀）

而证券代码唯一、且几乎总在首页表头行里。**标签不止一种**：
公告用「证券代码」、报告书用「股票代码」（实测 `D5-EQC-002` 用后者），两种都认。

### 2. 版本排序用**公告编号**，不用正文日期

正文里第一个日期常来自「历史沿革」章节 —— 实测出现过 `2008-02-14`、`2015-05-08`，
用它们排序会把版本链排乱。公告编号（形如 `2026-075`）按主体单调递增，是可靠的排序键。

**判「公告日期」属抽取语义**，索引层不替它决定。日期索引因此明确标注为「候选、未筛」。

### 3. 定不出发行主体的文档**显式列出**，不猜

`issuer_key_missing` 列出没有发行主体键的文档。**报「我定不出来」比给一个错的键有用。**

## 四、跨文件双侧出处（`pair_evidence.json`）

`tools/build_pair_evidence.py` 对宗博文封存的 20 组配对，输出**双方各自的块级锚点**：
共同的发行主体键及其出处块、各自的公告编号与日期候选、双方共同提到的主体名。

**它输出的是关联判断的输入，不是结论。** 本文件不判定是否同一事件。

### 与宗博文封存期望的对照（一次外部校验）

| 期望关系 | 组数 | 主体键一致 | 说明 |
| --- | ---: | ---: | --- |
| `related` | 4 | **2** | 另 2 组因 `D5-EQC-003` 无主体键而漏判（已显式报告，未猜） |
| `unrelated` | 16 | **0** | **零误报** |

**16 组对照零误报**说明「证券代码」这个键在关联信号上是干净的 ——
它不会把不相关的公告凑到一起。而 2 组 related 的漏判是**已知的键缺失**，
不是键本身错误。

**注意**：键一致只是**可核验的关联信号之一**，不等于同一事件。
同公司两份不同事项的公告，键同样会一致。

## 五、怎么复现

```bat
python tools\build_cross_index.py sample\D4\parse sample\D5\parse sample\D6\parse -o sample\D8\cross_index.json
python tools\build_pair_evidence.py --index sample\D8\cross_index.json --pairs evaluation\sealed\cross-doc\manifest.json -o sample\D8\pair_evidence.json
```

（`--pairs` 指向宗博文封存清单；该文件在 `zongbowen` 分支的
`evaluation/sealed/cross-doc/manifest.json`。）
