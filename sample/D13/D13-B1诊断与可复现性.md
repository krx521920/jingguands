## 二、D13-B1 的诊断

### 事实

| 来源 | sha256（前 24） |

**三个互不相同。**

### 我排除的可能

逐一试过常见序列化形式，**没有任何一种命中锁登记的哈希**：

| 序列化形式 | 命中 |

| 原样字节 | ✗ |
| `json.dumps(ensure_ascii=False)` | ✗ |
| `json.dumps(ensure_ascii=False, indent=2)` | ✗（**但与入库文件字节完全一致**） |
| `json.dumps()`（ASCII 转义） | ✗ |
| `json.dumps(indent=2)`（ASCII） | ✗ |
| 紧凑分隔符 | ✗ |
| 末尾加换行 | ✗ |

**入库文件本身是规范的 `json.dumps(ensure_ascii=False, indent=2)` 输出**，
所以「文件被别的工具重写过」这条也排除了。

### 判定

**锁登记的 `parse_sha256` 对应的是一份既非入库内容、也非当前源码可产出的第三份内容。**

但方向要说准 —— **不是「文件被改了」，而是「锁与文件不是同一次生成的产物」。**

## 三、附带发现：入库的 parse 用当前源码复现不出来

这是我在诊断 B1 时撞出来的，**比 B1 更值得处理**。

用 `zhangzhibo` 分支当前源码重跑同一份 PDF：

| | 入库 parse | 当前源码重跑 |
| --- | ---: | ---: |
| 块数 | **107** | **105** |
| 区域重建 | 104/107 = 97.2% | 104/105 = 99.0% |
| schema | `evidence/0.9` | `evidence/0.9` |
| `doc_id` | `d706bf32c` | `d706bf32c` ✓ |
| 形态 | TEXT | TEXT ✓ |

**`doc_id` 与形态一致，块数与分组不同。**

### 差异的性质：我在第一次判断上错了，这里更正

我最初判定「当前版本把表头合并成乱序块 → 回归」。**核查后收回这个判断**：

- pdfplumber 在该文档 p1 检出 `6×1` / `3×8` / `1×11`，p2 检出 `2×11` / `4×10` / `7×1`
- 我方检出 p1 `(3,8)`、p2 `(2,11)(4,10)` —— **被拒的都是单行或单列表**，
  按现有规则（`n_rows≥2` 且 `n_cols≥2`）**本来就该拒**，不是误拒
- **两份输出的表头都是乱序的**（入库版切成 3 块同样乱序，当前版并成 1 块也乱序）
- 两份的**绝对覆盖数相同（各 104）**，差异只在分组粒度

**所以这不是「新版本变差了」，而是「两份产物的块分组不同、质量同一档」。**
我先前那句「我引入了回归」下得草率，在此更正。

### 真正的问题：**不可复现**

不管哪份更好，**「用当前源码跑不出仓库里那份」本身就是缺陷** ——
它使「重跑验证」这条路径失效：第三方无法用源码复算入库产物。

**成因**：`parse_sha256` 与块分组都由解析器版本决定，而我在 D5/D6 期间
多次重生成了解析输出（表格检测修复改变了块切分）。**跨版本的 parse 文件不可复算**，
与 D9 的 `block_id` 漂移是**同一类问题的两个面**。

### 附带暴露的真实缺陷：多层表头阅读顺序

该文档的表头读出来是乱序的：

```
'…质权人质押名称大股东及其比例比例限售股起始日到期日'
```

这不是版本差异 —— **两份都乱序**。属**多层表头 + 窄列**的已知难点，
当前 `header_path` 拼接在列数多、列宽窄时不能恢复正确语序。

## 四、修复设计

### 对 B1（锁与文件不一致）

**根因是流程性的，不是代码性的。** 建议：

1. **锁里改记「生成时的源码提交 + 输入文件哈希」，而不是产物哈希。**
   产物哈希要求产物可复算，而解析器一改就全部失效；
   记源码版本 + 输入哈希，任何一方都能**自己重跑**验证。
2. 若必须记产物哈希，则**锁必须与产物在同一次提交里生成**，
   并在 CI 里加一条「重跑后哈希一致」的闸门 —— 否则锁必然腐化。

### 对「不可复现」

1. **入库 parse 必须标注生成它的源码版本**（parser 版本号目前是 `0.9.0`，
   但它没随块切分规则的变化而变 —— **这正是问题所在**）。
2. 建议**块切分规则变更即升 parser 版本号**，并在 manifest 里记录，
   让「这份 parse 是哪个版本产的」可查。

### 对多层表头乱序

已登记为边界（`src/finstruct/docs/解析能力边界表.md`），
**本轮不改** —— 修它会动 `header_path` 的拼接逻辑，风险高且需单独回归。
若要修，建议单独立项。
