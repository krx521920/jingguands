## 裁决 D13-A · 采纳张的**锁语义修正**（已实施）

**张的建议**：锁改记「生成时源码提交 + 输入文件哈希」，而非产物哈希。理由：产物哈希要求产物可复算，**解析器一改就全部失效，锁必然腐化**。

**我采纳，并已把 D13 锁升级为 v2**：

| 层 | 内容 | 性质 |
|---|---|---|
| **主锁** | `input_sha256`（PDF 哈希） | **不随生成器演进变化** |
| 生成器 | 解析器包路径 + `parser_version` + `schema_version` | 标识"哪一版产的" |
| 产物 | `product_sha256` | **降为"当次生成一致性核对"，非跨版本承诺** |

**实证依据（张提供）**：同一份 PDF，旧版解析 **107 块**、当前源码 **105 块**，绝对覆盖数相同、差异只在块分组——**产物哈希天然不可跨版本复现**。

**同时采纳张的第二条**：**块切分规则一改就升 `parser_version`**。现实测三份 parse 的 `parser_version` 均为 `finstruct.parse/0.9.0`——版本号在文件里有，但它**没随块切分规则变化而升**，所以"这份 parse 是哪版产的"仍查不出来。**责任方：张。**

## 裁决 D13-B · 纠正"第三份内容"结论

**张的结论**：锁登记的 `parse_sha256` 对应"一份既非入库内容、也非当前源码可产出的**第三份内容**"。

**这个结论不成立**——他的排除矩阵**缺了行尾变换**。他列的 7 种形式（原样 / `ensure_ascii` / `indent=2` / ASCII 转义 / ASCII+indent / 紧凑 / 末尾换行）**没有一种涉及 CRLF↔LF**。

**我的实测链（完整、可复现）**：

```
STR-04
  锁值                 c95ebe93a45216b8…
  我磁盘文件（CRLF）     c95ebe93a45216b8…   ← 与锁值一致
  LF 归一后             c348c48b3d1235bb…   ← 与"入库实算"一致
  入库文件（纯 LF）      c348c48b3d1235bb…   ← 张的"入库实算"
```

**磁盘 CRLF 归一后 == 入库 LF** —— 同一内容、只差行尾。**不是"第三份内容"，是同一份的 CRLF 版本。** 成因是我在 Windows 上对工作区文件算哈希，而 git 提交时做了 CRLF→LF 规范化（`.gitattributes` 已修此根因）。

**张的第三条哈希 `8175e7e7…`（当前源码重跑）是另一回事**——那是"源码版本不同"，属上面 D13-A 的范畴，**不是"锁错"**。

**判定**：张的**方向判断（不是文件被篡改）正确**，但**"第三份内容"是测试矩阵缺口的产物**。建议他复核矩阵时补上 `\r\n` 变换这一维。

## 裁决 D13-C · 魏的两项

### C1 · guarantee（银行担保）不进 v0.3 —— **采纳"不做"**

魏的理由（首测已按 v0.3 锁存、新增事件类型＝分母全链变动、14 天窗口不支持）成立。

**我这边理由更硬**：我签署的裁决含**锁定项「不改 Gold / 不改封存集」**。新增事件类型会直接改动分母与全链，**破坏首测锁存**。故：

- **D14 封版前不扩枚举**；
- 若评审问及，口径＝「本项目范围三类事件（质押 / 股权变动 / 中标），担保属范围外业务形态，**边界如实登记**」；
- 若将来要扩：走 `interface/README.md` 第八节正式变更流程（登记 → 五方同步 → 评测侧重验）。

### C2 · `standardized=false` 判定口径 —— **采纳登记，并当场裁决 text 毛刺**

**采纳魏的 W3 判定表**，登记为签署表附录：

| 情形 | `standardized` |
|---|---|
| 数值/日期类 + `status=extracted` + 方 normalize 成功 | `true` |
| 同上但 normalize 拒绝（依据不足/双币种无明示/单位冲突） | `false`（错误入 `run_meta.errors`，不静默修） |
| `extracted` 但 `raw_value` 缺失（模型给计算值无依据） | `false` + note"计算值待核" |
| 无值族（`not_mentioned`/`needs_review`/`unreadable`/`not_applicable`） | `false` |
| **`text` 型字段** | **恒 `false`** |

**text 毛刺裁决**：魏报「text/extracted 存在 4 例 `false` 与多数 `true` 并存」。他自己写明「**text 不进标准化层、无契约含义**」——**既无契约含义，就该恒 `false`**，不应随模型输出漂移。

**但不改 Gold**：修改既有 Gold 的字段值会破坏封存锁存（同 C1 的锁定项）。故采用**消费侧裁决**：

> **`text` 型字段的 `standardized` 键无契约含义，消费方不得读取**；页面对 text 字段**不显示"标准化"状态**。

此条登记进签署表附录，**不动 schema、不动 Gold**。
