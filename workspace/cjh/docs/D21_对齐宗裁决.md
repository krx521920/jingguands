## 二、锚点核对：本地实算 = 宗登记值

**没有抄他的数字**，按他的算法自己算了一遍：

```
本地 data_unified/ 32 份 → 排除 DEMO-EQC-HL-0930.json → 31 份
实算 anchor_sha256 = 381c760fa07b2dc3a8256282e23009bce4b79445fdc7f4f4280168af6c90cef0
宗登记             = 381c760fa07b2dc3a8256282e23009bce4b79445fdc7f4f4280168af6c90cef0
逐份比对：31/31 一致，不符 0 份，本地多出 0 份
```

**为什么必须实算而不是抄**：抄数字的话，本地批次一旦漂移，页面照样显示"锚点一致"——那就把宗设的锚点机制变成了摆设。已用反证验证判别力：**篡改 1 份文件（加一个探针字段）后实算变为 `715bba74994e0be0`，漂移被检出**。

## 三、★ 落地过程中查出一件比裁决本身更重要的事

按 R4 做"同源变体检测"时（同一 `file_sha256` 聚类），检出 **21 组**，不是预想的 1 组：

| 组数 | 情形 | 内容 |
|---|---|---|
| 20 组 | 事件数一致 | `D5-EQC-00x` ↔ `wei_real_eqc_00x`、`D6-AWD-00x` ↔ `wei_real_awd_00x` —— **同一 sha、同一 parser 0.9.0、字段名集合完全一致、事件数一致** |
| 1 组 | 事件数不一致 | `D4-PLD-001`(3 事件) ↔ `wei_real_pledge_0197`(1) ↔ `wei_real_pledge_ce37`(1) —— P0-01，已知 |

内容级反证（不能只凭 sha）：抽 3 组比对字段名集合与 parser 版本，20 组确实一一对应、逐项一致。

### 这推翻了 D19 的一处表述

D19 我写的是「**两目录文件名零重叠**」——这句话**对文件名成立，对内容不成立**。实际是同一批公告用了两套命名（`D5-EQC-xxx` 与 `wei_real_eqc_xxx` 指向同一份 PDF 的同一次抽取）。

**这才是"两个数并列"的真正来源**：不是"两个不同样本"，而是**同一批样本被改名后当两批统计**。当时若只按文件名判断，会得出"样本不同源"的结论——方向错了。

### 对 R4 的影响

宗 R4 的验收标准第 4 条是「存在同 `file_sha256` 多份输出时，页面标注了同源变体关系」。若只标 P0-01 那 1 处，**另外 20 处仍会被显示成"两个独立 case"**，等于没做。

因此实现上**按 sha 自动聚类，不依赖人工登记**——将来出现第 22 组会自动进登记区。
