# M-2 仓库瘦身评估与方案（陈家浩 · 2026-10-15）

> 触发：领导 21:35 授权继续处理待办总表 §2 的 **M-2**。
> **结论先行：不建议执行 `git filter-repo` 重写历史。** 该待办的前提（「每个 clone 背 21MB 演示媒体」）已过期，实测收益≈0，而风险为全仓最高。
> 本文只出方案与取证，**未对仓库历史做任何改动**（重写历史须领导单独授权，本文不构成该授权）。

## 1. 取证：瘦身前提已不成立

| 待办表原话 | 实测结果 | 证据命令 |
|---|---|---|
| 每个 clone 背 **21MB 演示媒体** | 媒体/压缩包合计仅 **6.2 MB**（mp4 1 个 6.5MB、png 31 个 5.3MB；zip/gz/pdf/jpg/webp/ico 均为 **0 个**） | `git ls-tree -r -l HEAD` 按扩展名汇总 |
| 需 `git filter-repo` 重写历史 | 本仓**已是 `blob:none` 部分克隆**（`remote.origin.promisor=true`、`remote.origin.partialclonefilter=blob:none`）⇒ 新 clone **不下载全量 blob**，按需懒加载 | `git config --get remote.origin.promisor` |
| —— | 历史极小：`git rev-list --count HEAD` = **8 个提交**；`.git` 仅 **163 MB**（其中对象 154 MB） | `git rev-list --count HEAD` / `du -sh .git` |

**也就是说：filter-repo 能删的只有「历史中存在、现已删除」的 blob。而本仓只有 8 个提交、且已是部分克隆——可删的增量≈0。**

**HEAD 被跟踪树 = 360.6 MB / 17,244 个文件 / 均值 21.4 KB**。按扩展名：

| `.jsonl` / `.yaml` / `.mjs` | 8.9 MB | 3,523 | 数据/配置/脚本 |

**360 MB 是当前工作树内容，是「正在用的数据」，不是「该清的历史」。** 清它等于删数据，不是瘦身。

## 3. 风险：为什么尤其不能重写历史

`git for-each-ref` 实测 **27 个引用**，其中远端 **26 个分支 + 本地 3 个 tag**：

- 队友全员分支：`origin/feature/wei-core`、`origin/feature/zhang-parser`、`origin/feature/fang-rules`、`origin/weiwenyu`、`origin/zhangzhibo`、`origin/zongbowen`、`origin/inbox/*`（4 个）
- 主干与交付：`origin/master`、`origin/develop`、`origin/delivery/v2.0`～`v2.0.3`、`origin/eval/baseline`、`origin/fix/*`、`origin/fxc178-patch-1`
- 本地交付 tag：`v1.0-d14-release`、`v1.1-final`、`v2.0-delivery`

**一次 filter-repo 会让以上全部 SHA 失效**：全员 clone 失效、交付 tag 失去对应物、我方文档与守卫里引用的锚点 SHA（如 P0-01 的 `D4-PLD-001` sha256 证据链、评测成绩单指纹）全部对不上。**收益≈0、成本=全团队重克隆。**

## 4. 真要瘦身，可做的三项（均不需重写历史）

按「性价比 × 是否需队友配合」排序，**都只减当前树、不动历史**：

| # | 事项 | 可省 | 归属 | 前置 |
|---|---|---|---|---|
| S-1 | **去重复**：`D5-EQC-002` 同一份 1.84 MB JSON 有 **6 个副本**（`tools/fang-attribution/public_dev_D9/parse_D9/`、`corpus/zhangzhibo/d5/parse-official/`、`corpus/zhangzhibo/d5/parse/`、`corpus/zhangzhibo/d5/parse/equity-002.parse.json`、`corpus/zongbowen/d5/raw/`、`evaluation/D5/dev/raw/`）≈ **11 MB**；`D5-EQC-001` 同构 **6 副本** ≈ **6.4 MB**。合计 ≈ **17.5 MB** | ~17.5 MB | 张智博 / 方轩诚 / 宗博文（三方目录都有副本） | 须三人确认哪份是权威、其余改引用 |
| S-2 | **跑批产物外移**：`runs/d10-b-enriched.json` 7.46 MB、`runs/fang-report-D10/*` 1.30 MB 等 `runs/` 下产物 | ~9 MB | 方轩诚（`runs/`） | 确认无人以路径直读 |
| S-3 | **schema 历史版本外移**：`docs/persistence-changes/historical-formats/v0~v3.schema.json` + `releases/` 共 **7.2 MB** | ~7.2 MB | 魏文宇（`docs/persistence-changes/`） | 确认版本演进史无引用需求 |

三项合计约 **33.7 MB**，仅占 HEAD 树 **9.4%**；且全部要动队友目录 ⇒ **我方不代动**，只登记。

## 5. 建议处置

1. **M-2 原方案（filter-repo）关闭**，理由见 §1/§3：前提过期 + 风险最高 + 收益≈0。
2. **改为登记 S-1 / S-2 / S-3**（§4），交给对应队友按目录归属自行决定；我方只提供体积取证，不代删。
3. 若领导的目标是「让新同事 clone 更快」——**该目标已由 `blob:none` 部分克隆达成**，无需额外动作；可在 README 注明 clone 时加 `--filter=blob:none`。
4. 若领导的目标是「`.git` 占空间」——`git gc --prune` 一类常规维护即可，**不触碰历史**。
