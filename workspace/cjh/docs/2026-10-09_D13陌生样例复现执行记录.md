## 二、缺陷 D13-B1（阻塞级）：`parse_sha256` 与入库 parse 文件不一致

### 事实

| 样例 | 锁登记 `parse_sha256` | git 对象实算 sha256 | 判定 |
|---|---|---|---|
| STR-04益生股份 | `c95ebe93a452…` | `c348c48b3d12…` | ❌ 不符 |
| STR-05 侨银股份 | `f45da7f0f36c…` | `15e2331cfb29…` | ❌ 不符 |
| STR-06 力勤资源 | `9441f6b168b7…` | `dc0bddda6632…` | ❌ 不符 |

对照组：`file_sha256`（PDF）**3/3 全部一致**，说明取样管道本身没问题。

### 已排除的可能原因

| 假设 | 验证方式 | 结果 |
|---|---|---|
| 我取样时shell 转码污染 | `git cat-file blob` 直读对象重算 | 排除（对象本身即 `c348c4…`） |
| CRLF / LF 行尾差异 | LF 归一化后重算 | 排除（归一前后同值） |
| 文件末尾空白差异 | 去尾空白后重算 | 排除 |
| 锁写的是 git 对象名而非 sha256 | `git rev-parse` 取 blob 名比对 | 排除（`9630dd…`/`ccf2fd…`/`f46f73…` 亦不符） |
| 锁在 parse 文件改动之后写| 查锁与parse 的提交历史 | 排除（锁自 `a6a34097` 起未改，parse 亦未再改） |

### 性质

锁文件与其所锁对象自相矛盾，**在任何口径下都无法同时成立**。
后果：`parse_sha256` 这一条防篡改承诺当前**不可验证** —— 它既不能证明 parse 未被改，
也不能证明 parse 未被改而只是锁写错。二者对复现结论的影响完全不同于"只是哈希写错了"。

### 请宗裁定（我不自行认定）

1. 是锁里的 `parse_sha256` 登记错了（应按入库文件重算），还是
2. 入库的 parse 文件不是宗原本打算锁的那一版（则应重新入库并重锁）？
