# D15转接口改为契约优先 —— 交付说明

>领导指示（2026-10-08）：「转接口优先按照契约进行」，并提供《项目计划书-可信公告事件提取与跨文档核验.docx》作为**建议性文件**供参考。
> 本轮结论：转接口原先产出的是**页面私有约定**，与正式契约 `interface/event-envelope.schema.json` v0.3 全不一致。已改为契约优先，两层分离。

---

## 一、为什么要改（改造前的实测差距）

改造前 `upstream_bridge.js` 的产出与正式契约逐项对不上：

| 层 | 契约 v0.3 要求 | 改造前实际产出 | 后果 |
|---|---|---|---|
| 顶层必填 | `is_mock` / `source` / `run_meta` | 全缺 | 契约校验器直接判不合规，无法入库 |
| 顶层多余 | `additionalProperties=false` | 多出 `data_mode` `source_file` `evidences` `bridge` `integrity` | 违反契约，评测方一验即挂 |
| 字段名 | `raw_value` / `value` / `standardized` / `status` / `provenance[]` | `normalized` / `evidence_id` / `status_override` | 字段名对不上，任何自动校验都无从下手 |
| 出处结构 | 内嵌 `provenance[]` | 外置 `evidences[]` + 字段挂 id | 出处与字段分离，易断链 |

**关键判断**：计划书 §三/§四 那些可核验设计（出处随数据生成、口径作为数据字段、错误填充率单列）**全部以正式契约为载体**。页面私有字段既不能机器校验，也不能直接入库给评测方 —— 计划书 §九「输出格式合规率 100%」在旧结构下**根本无法核**。

---

## 二、改法：契约为本体，视图为投影

```
上游信封 (魏 v0.3 / 方 records)
        │
        ▼
bridge/upstream_bridge.js  ← 唯一转换点
        │
   ┌────┴─────────────────────────────┐
   │ envelope                view│
   │ 严格符合 schema v0.3              │ 从envelope 派生
   │ additionalProperties=false       │ 页面渲染用
   │ 可机器校验 / 可入库 / 可给评测方    │ 前端零改动
   └────┬─────────────────────────────┘
        │                    │
        ▼                    ▼
/api/contract          /api/result 等15 个接口
（新增，契约本体）        （返回 view，结构与改造前一致）
        │
        ▼
bridge/contract_validate.js（两层机器校验）
```

**核心纪律三条**：

1. **视图字段绝不写进 envelope**。契约 `additionalProperties=false`，塞进去即违规。
2. **视图只能从 envelope 派生**，不允许独立维护 —— 不存在两份真源。
3. **不合规数据如实上报，不静默修好**。转接口是通道不是裁判：它如实报告"这份数据不合契约"，比替上游改数据更诚实。抹掉违规＝掩盖错误填充率这个一级指标。

## 三、新增：`bridge/contract_validate.js` 零依赖契约校验器

不用 ajv：本项目不装依赖，且手写校验器能给出**人话错误信息**（"哪个队友的哪个字段错了"），ajv 的报错对此不可读。

**两层校验**：

| 层 | 校验内容 |
|---|---|
| **L1 JSON Schema** | 顶层 6 项必填、`additionalProperties=false`、枚举、类型、`event_id` pattern `^E[0-9]+$`、`quote` minLength |
| **L2 字段注册表** | 字段名在注册表内？`unit` 与注册表一致？`denominator` 是否满足 `fixedDenominator`/`requiresDenominator`？ |

**注册表直读不手抄** —— 从 `spec/v0.3/registry.mjs` 解析出 3 事件类型 / 37 字段。**解析失败直接抛错，绝不返回空注册表**：空注册表会让所有字段"合规"，与 D10 造假同款。

**校验器自身也被守卫**：`_contract_check.js` 第1 节用 8 类真违规测它（schema_version 错、is_mock 类型错、缺 file_name、多余顶层键、event_id 违规、event_type 越界、字段越界、unit 不符），**必须 8/8 全抓** —— 只会说 OK 的校验器等于没有。

**额外把计划书 §四 变成机器断言**：

- §四.1 模型只找数不算数 → 转接口**零数值运算**（value/raw_value 原样搬运，有守卫数着）
- §四.2 出处随数据生成 → 有值字段必有 `provenance` 且 `quote` 非空；表格出处必须定位到单元格
- §四.4 错误填充率 → `not_mentioned`/`not_disclosed`/`not_applicable` 却带值 = 机械证据，报 error

## 四、错误填充率：从"写在计划书里"变成"跑出来的数"

计划书 §四.4 要求把"原文没有、系统却给出一个值"单列为一级指标。现在它是接口的一部分：

```json
"error_fill_audit": {
  "phantom_count": 0,
  "fields_compared": 6,
  "phantom_fields": [],
  "reads": "状态声明「原文未提及/未披露/不适用」却带着取值 —— 属计划书 §四.4 的错误填充，原样上报不抹除"
}
```

**处置原则：原样上报，不抹除**。抹掉值＝替上游改数据＝这个一级指标就永远测不出来了。守卫里明确断言"原值保留"。

## 五、页头徽标：结论必须上屏（反造假铁律第4 条）

计划书写了"合规率 100%"和"错误填充率 ≤5%"，如果只躺在 JSON 里，读者眼中等于没做。所以页头加了徽标：

```
契约违规 2 · schema 1 · 注册表 1 · 错误填充 1/1
```

**三态区分**（关键）：`契约合规` / `契约违规 N` / `旧版数据 v0.1（非 v0.3 契约）`。D1 骨架期的 v0.1/v0.2 数据本来就不合 v0.3，全报成"违规"会淹没真正的新错误。

悬停 title 展开：合规率口径、逐条违规明细、错误填充字段清单、计划书条款引用。

**`demo/_shot_contract.py` 18 项断言**，其中最关键一条：**注入违规数据，验证徽标真的会变红**。只测合规态的截图自检，会漏掉"徽标写死了 pass"的造假 —— 与 D10 `web_cli_same_result` 同一坑。

## 九、新增接口

### `GET /api/contract?dataset=<id>`

返回**契约本体**，供下游入库 / 评测方使用。

| 字段 | 说明 |
|---|---|
| `envelope` | 严格符合 schema v0.3 的信封，`additionalProperties=false` |
| `validation` | 两层校验结果（`ok` / `errors[]` / `layers{schema,registry}` / `is_stale_version`） |
| `schema_file` | 契约来源 `interface/event-envelope.schema.json` |
| `registry_source` | 注册表来源（直读 `spec/v0.3/registry.mjs`，不手抄） |
| `relation` | 视图与契约的关系说明，防止下游误把视图当契约入库 |

## 十、计划书 → 转接口的对应关系（建议性采纳）

计划书是**建议性文件**，不是强制规范。本轮采纳为机器断言的部分：

| 计划书条款 | 采纳为 | 落地位置 |
|---|---|---|
| §三.2(2) 字段不存在标"原文未提及"，不猜不留空 | 契约 6 态 | `not_mentioned` 显式进 `fields`（不再"不产出字段"） |
| §四.1 模型只找数、不算数 | 守卫断言 | 转接口零数值运算，13 字段数过 |
| §四.2 出处随数据生成、四级定位 | 守卫断言 | 有值字段必带 `provenance`；`cell` 必带 `table_id`+`cell_ref` |
| §四.4 错误填充率单列一级指标 | 接口字段 | `error_fill_audit.phantom_count` |
| §九.5 输出格式合规率 100% | 页头徽标 | `contractBadge` 三态显示 |
| §五/§六 协作机制 | 未变 | 评测标准仍由宗独立维护，开发不得改 |

**未采纳为代码约束**：§九 的具体指标阈值（≥90%/≥98%/≤5% 等）—— 这些是**目标值**，不是实测值，代码里填进去就是"未测项填目标值"，与 D12 立下的纪律冲突。仍留在 `metrics_registry` 里作 `status=not_covered`。

## 十三、可复用经验（写给下一个改这块的人）

1. **"页面能用"不等于"契约合规"**。改造前页面跑得好好的，但契约一项都不合。**页面私有约定不能代替契约** —— 契约是给下游和评测方的，页面只是它的一个消费者。
2. **两层分离优于原地改造**。直接改字段名会炸掉 38 处前端消费点；改成"契约本体 + 视图投影"，前端零改动，还顺手多了一个可入库的出口。
3. **校验器自己要被测**。只会说 OK 的校验器比没有更危险（假安全感）。守卫必须先测"它能不能抓出 8 类违规"。
4. **注册表直读，不手抄**。手抄的 unit 映射表必然与上游漂移（这次方口径 `unit` 兜底 `"text"` 就是手抄式猜想的产物）。
5. **不合规要如实报，不要静默修好**。本轮徽标把 `bank_guarantee`（v0.1 旧数据）报出来，第一反应是"工具误报"，查完发现是**真的不合规** —— 只是该归类为"旧版数据"而非"违规"。区分三态既不掩盖问题，也不淹没真问题。
6. **截图自检必须测"失败路径"**。只截合规态的图，会漏掉"徽标写死 pass"的造假 —— 和 D10 `web_cli_same_result` 同一个坑。注入违规数据看它变不变红，才是真断言。
