## 二、本步挖出的两个真问题（比清单本身更重要）

### ★ 问题 1：`parity_report.js` 里"说了没做"的 stale 检测

文件头注释白纸黑字写着：

> 报告存在但 `generated_at` 早于数据源变更 ⇒ **带 stale 标记，页面须提示**

**代码里从未实现** —— 一条"读者以为有保护、实际没有"的注释。
更糟的是：报告本身也已过期（10-08 生成，指纹里 `page_data` 只有 `data/` 41 份，
换源后页面跑 `data_unified/`，**报告里的数字不描述当前页面所用的数据**）。

**落地**（`bridge/parity_report.js`）：
- 新增 `staleness(r)`：**实算当前两批目录指纹，与报告存的 `input_fingerprint.inputs` 对账**。
- 不一致 ⇒ `verdict:"stale"`（原 `measured`）、带 `stale_reason` 与 `how_to_regenerate`，
  **但保留原数字并标明** —— 删掉等于把"曾经跑过"也抹了。

> ★ **判过期用指纹而非日期**：日期会被"同一天改了数据"骗过去，指纹不会（D19 铁律⑧）。
> ★ 踩了一次坑：键名必须与 `metrics_registry.fingerprint()` 的 `{page_data, unified_batch}` 一致，
> 我第一版按 `data_source` 的批次 id（`authoritative`/`legacy`）去找 ⇒ **恒判 stale**。
> **恒真的判据和恒假的判据一样有害** —— 那会让"过期检测"变成"永远报警"。

### ★ 问题 2：L3 导出对照的**基准错配**（重跑时才暴露）

宗给的两个选项是"重跑 或 标注"。我先重跑，结果 L3 从 `idempotent 16/16`
**掉到 `divergent 1/16`** —— 这么大的反转不可能是导出链路坏了。查下去：

```js
// 脚本原写法（本地侧）              // HTTP 侧（server.js）
toContract(readJson(DATA_DIR/ds))   readDataset(ds)
   ↑ 契约信封 + 旧目录                 ↑ view 投影 + data_source 解析 + extraction_engine
```

**两侧压根不是同一个对象**，比出来的 divergent 是基准错配，不是链路走样。
更早还有第二层：脚本里的 `csvBytes()` 是 `contractToCsvRows()` 的**手抄版** ——
server 改一列规则这里不跟着改，L3 就会常亮红灯。

**修法（原则：不许出现第二份真源）**：
1. `server.js` 末尾加 `require.main` 守卫＋导出 `readDataset` / `contractToCsvRows` /
   `csvEscape` / `CSV_COLUMNS`。**`node server.js` 行为完全不变**（守卫内才 `listen`）。
2. `_parity_real.js` 本地侧改为 `require("../server.js")` **直接复用同一批函数**。
3. L3 数据集选取从"只取 `data/` 前 8 份"改为**两批各取**（权威批 5 + 演示池 3）——
   原写法换源后验的全是"页面已不再使用的那批数据"，验了也白验。
4. **两侧一致地拒绝**（`upstream_case` 是测试夹具、被 `listFilesIn` 排除、本地取不到 + HTTP 404）
   单列为 `unavailable[]`，**不进分子分母** —— 算进 divergent 就永远是 divergent。

**重跑结果：L3 = `idempotent 16/16`**（HTTP 16 成功），L1 `distinct` 22 对，L2 `divergent` 372/382。

> ★ 顺序有意义：**先修基准再重跑**。若照宗的第二选项只"标注仅对 10-08 输入有效"，
> 这个错配会一直藏着，将来 `readDataset` 一改字段名，L3 就变成没人能解释的红灯。
