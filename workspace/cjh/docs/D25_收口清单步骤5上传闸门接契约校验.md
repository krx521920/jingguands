## 一、缺陷复现（先复现再动手，不照着清单改）

宗清单步骤 5 的原文：

> 上传时调用 `bridge/contract_validate.js`：缺 `run_id`/`is_mock`/`source`/`run_meta` 的件不能判 `ok:true`。
> **验收**：上传 `{"schema_version":"0.3","events":[]}` → `ok:false`（或带 `contract_ok:false`）。

修复前实测（`curl -X POST -F file=@…`打真接口，非读代码猜）：

| 位置 | 结论 |
|---|---|
| `POST /api/upload` | **`ok: true`**，并落盘进 `data/_p1_2_probe.json` |
| `contract_validate.validate()` 对同一件 | **`ok: false`，4 条 error**（缺 `run_id`/`is_mock`/`source`/`run_meta`） |
| `/api/contract` 机检 | **`ok: false`** |

**＝同一件东西两处结论相反。** 页面的「契约合规」和入库闸门各信一处，
合规率就成了假数字 —— 与 D10「未接通即回落」、D19「实算的不是当前数据」同款。

根因：`processUploadFile()` 的三道检查全是**形状检查**
（非 `.json`／非空／有 `events` 数组／有 `schema_version`），
**没有一道是语义检查**。`toContract()` 那次调用是"干跑"，
它的 `contract_validation` 返回值被丢掉了（`toContract(parsed);` 连变量都没接）。

## 二、落地（三处，判定逻辑只有一份）

### 1. 上传闸门接机检 —— `server.js` `processUploadFile()`

```js
const bridged = toContract(parsed);
const cv = (bridged && bridged.contract_validation) || {};
entry.contract_checked = true;
entry.contract_ok = cv.ok === true;
if (!cv.ok) {
  entry.ok = false;
  entry.error = "契约校验未通过（v0.3）：" + (cv.errors || []).slice(0, 5).join("；");
  entry.contract_error_count = cv.error_count || 0;
  entry.contract_errors = (cv.errors || []).slice(0, 10);
} else { /* 落盘 */ }
```

**只拒硬违规，如实说缺哪几个字段，绝不静默补齐** ——
补齐等于伪造"这份数据本来合规"，与 D15「不合规数据如实上报不静默修好」同纪律。

### 2. `datasets.sources[].contract` —— `bridge/data_source.js`

新增 `contractStatusOf(json)`，**走 `toContract()` 拿现成的 `contract_validation`**，
不自建第二份判定（两处各判一次迟早漂移，那是"同一指标两处对不上"的同款漏洞）。

★ **刻意经`toContract` 而非直调 `contract_validate`**：旧版 v0.1 件要经
`fromLegacyEnvelope()` 兼容后才谈得上合规（`pledge` 19 违规→0），
直调会把"兼容后 0 违规"的旧件误报成违规。

实测 **62 份全部带 `contract` 字段，唯一不合规是 `bank_guarantee`（1 条）** ——
即`guarantee` 事件类型不在 v0.3 三类内。**继续不硬塞成 pledge**，如实标出。

### 3. 报告条目三态显式化 —— `server.js`

`entry.ok` 原先在失败分支是 `undefined` 而不是 `false`。
消费方 `if (r.ok)` 能判false，但 `r.ok === false` 的严格比较会漏判，
下游"有没有失败项"就算错。已在函数出口统一 `if (entry.ok === undefined) entry.ok = false`。

★ 这条是**守卫跑出来的真缺陷**，不是我预先想到的：守卫第一版
`e1.ok === false` 判 FAIL 而 `error` 已正确 ⇒ 说明 `ok` 确实是 `undefined`。

## 三、守卫 `demo/_p1_2_check.js`（9 项，含反证）

范式照 `_d13c2_check.js`（零依赖、起服务、JSON 结论、`FAIL=1` 退出）。

| 段 | 项| 断言 |
|---|---|---|
| A | A1 | 空壳件被拒（宗的原始复现路径） |
| A | A2 | 拒绝原因**定位到具体缺失字段**，不是一句"校验失败" |
| A | A3 | 报告带机器可读字段（`contract_ok` / `contract_errors[]`） |
| A | A4 | **不合规件不落盘**（落盘了就会被 metrics 读走） |
| A | A5 | **合规件必须能收** —— 否则闸门是"一律拒收"，另一种造假 |
| B | B1 | `sources[].contract` 字段齐全 |
| B | B2 | **清单与 `/api/contract` 对同一件同结论**（抽查 3 份） |
| B | B3 | 不合规件如实标出、未被藏起来 |
| C | C_PROVE | **反证**：短路闸门后必须 FAIL（默认 skip，`--prove` 才跑） |

**反证结果**：把 `if (!cv.ok)` 改成 `if (false)` 后，空壳件立刻 `ok=true` 被放行
⇒ 证明本门的 FAIL 条件正是这条闸门，不是恒返回 0。**反证跑完自动复原 `server.js`。**

### ★ 写守卫时自己踩的一个坑（值得记）

第一版「合规基准件」的 `run_meta` 我写成`{engine, generated_at}`，
结果 A5 FAIL。查契约才发现 **`run_meta` 是 `additionalProperties: false` 的封闭对象**，
白名单只有 `entry`/`model`/`started_at`/`duration_ms`/`code_version`/`interface_version`/`errors`。

> **自造"合规样例"时必须照契约的白名单逐字段对，不能凭直觉命名** ——
> 否则守卫会把"闸门只认我这一种写法"报成"闸门一律拒收"，
> 而真缺陷（`ok: undefined`）被淹没在这种噪声里。
