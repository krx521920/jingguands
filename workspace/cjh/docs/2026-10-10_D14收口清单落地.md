### 2.2 关系判定改读 `expected_relation`（含缺陷修复）

**原实现是真缺陷**，不是"顺手优化"：

```js
// server.js 旧代码（已删）
function expectedRelationOf(text) {
  if (s.includes("unrelated")) return "unrelated";
  if (s.includes("related"))   return "related";
  if (s.includes("unknown")||s.includes("insufficient")) return "unknown";
  if (s.includes("explainable_difference")) return "unrelated"; // ← 元凶
  return null;
}
```
调用处：`expectedRelationOf(exp.expected)`（读自然语言字段做关键词映射）。

**实测错例D10-INT-008「币种折算跨文档」**：

| 来源 | 值 |
|---|---|
| 权威包 `diffs.relation` | `unknown`（证据不足，保留疑点） |
| 旧关键词映射 | `explainable_difference` → **`unrelated`**（不同事件）❌ |
| `fang_report_bundle.json` 内该条 | `plugin_relation="unknown"` 而 `builtin_relation="unrelated"` ← 同一条自相矛盾 |

**根因**：原 `expected` 字段把**归因层**结论（`explainable_difference`／不判矛盾／无强制换算）
写进了 **relation 层**预期，两层口径混写，关键词映射必然误判。
魏《D14-INT008判定口径》已拆分为：`expected_relation`（relation 层唯一真源）
＋`attribution_demo`（归因层展示）＋`expected_text_legacy`（留档，**禁止机器读取**）。

**新实现**：

```js
const RELATION_ENUM = new Set(["related", "unrelated", "unknown"]);
function expectedRelationOf(exp) {
  const v = exp && typeof exp === "object" ? exp.expected_relation : null;
  if (v == null) return null;                 // 未登记 → 不猜
  const s = String(v).trim().toLowerCase();
  return RELATION_ENUM.has(s) ? s : null;     // 不在枚举 → 不猜
}
```
接口新增两个字段：`expected_relation_source`（标明来源，缺字段则报"未登记"）、
`attribution_demo`（归因层展示，relation 层不读）。
`expected` 仍透传页面显示，但**不参与任何判定**。

`check-snapshot-coverage.mjs` 报的 `materialized_bad=3`，三条**全部是演示件**：

| `DEMO-EQC-HZ-RESULT` | 同目录 | `a18772768eb1becf…` | `6b77be1ae3a3…` |

### 我已核实的事实

1. **三条在权威批里都没有对应信封**。权威 31 份信封中，DEMO 只有 `DEMO-EQC-HL-0930`
   （且按 R1/锚点口径已排除）；`DEMO-EQC-HL-SIMPLE` 与 `DEMO-EQC-HZ-RESULT`
   连信封都不在 `data_unified/` 里 —— 它们是 D8 时期的演示补料，不属权威批。
2. **它们在源树有多处副本**：`delivery/v2.0` 里这三个名字分别出现 **7 / 6 / 6** 处。
   这与 D19 查出的「21 组同源变体」是同一形态问题（同内容多副本、命名沿用），
   按sha 取件时命中哪一份取决于路径而非内容。
3. 因此 `materialized_bad=3` **不影响权威口径的任何数字**：31/31 文档、451/451 锚点均达标。
