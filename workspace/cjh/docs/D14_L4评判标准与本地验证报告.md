## 一、为什么要先统一判据（这是 L4 真跑前唯一的卡点）

原先 `extractor.diffEnvelopes()` 用 `JSON.stringify(a) === JSON.stringify(b)`逐字段比 value，也就是**逐字节全等**。

这个判据对确定性程序成立，对 LLM 抽取**必然大面积飘红**：同一个模型跑两遍，`1,200,000股` 与 `1200000`、`2026年10月8日` 与 `2026-10-08`、`1.2亿元` 与 `120000000` 全都语义相同、字节不同。

于是真跑出来会是这样：

| 假设 | 报告上的话| 问题 |
|---|---|---|
| 严格判据 + 200 处差异 | 「Web/CLI 不一致」 | **没有信息量**：190 处是格式差异，10 处是真缺陷，混成一句话，说服不了任何人 |
| 为了好看放松判据 | 「一致率 99%」 | **D10 造假的同款**：判据一松，真缺陷和格式噪声一起被吞 |

所以判据必须**事先写死、分层、可复核、可追溯**，而不是跑完看着结果再定。

## 二、五级判据（S0..S4）

从硬到软，逐级放宽。**硬级别一票否决，不许用软级别的高一致率去掩盖。**

| 级 | 名称 | 比什么 | 是否否决 | 为什么放这一级 |
|---|---|---|---|---|
| **S0** | 结构一致 | 事件条数、业务键集合 | ✅ | 漏抽整条事件 = P0，比字段差异严重 |
| **S1** | 存在性 + 6 态状态 | 字段在不在、`status` 六态 | ✅ | 一边抽到一边弃权 = 抽取率被吞 |
| **S2** | 取值一致（归一化后） | 字段值 | ✅ | 抽出来的对不对 |
| **S3** | 出处存在 | 有值字段是否挂了锚点 | ✅ | 抽对了能不能验 |
| **S4** | 原文 quote 摘录 | **不比** | ❌恒真 | LLM 有温度，摘录必然不同 |

### S4「不比」是本判据最重要的决定

把原文摘录逐字相比，等于要求 LLM 连标点空格都复现。**摘录不同不构成抽取不一致**，只说明"两遍摘了同一段原文的不同长度"（见下方 `awd_007` 的真实例子）。它归入出处核验（`_evidence_quote_real.js`）单独验，不混进 Web/CLI 对照。

## 三、归一化规则（9 条，只消书写差异）

**铁律：只允许消除书写差异，不允许改变数值含义。**

| ID | 规则 | 例 |
|---|---|---|
| R1 | 全角转半角 | `ＡＢＣ` ≡ `ABC` |
| R2 | 去首尾空白 + 折叠 | `　张三　` ≡ `张三` |
| R2b | 去句末标点 | `…被动稀释。` ≡ `…被动稀释` |
| R3 | 数值书写（千分位/尾零/前导零） | `12,000,000` ≡ `12000000` |
| R4 | 百分号 = 百分点 | `2.5%` ≡ `2.5` |
| R5 | 中文数量单位换算 | `1.2亿元` ≡ `12000万元` ≡ `120000000` |
| R6 | 日期归一 | `2026年10月8日` ≡ `2026-10-08` |
| R7 | 区间分隔符 | `2026-01-01至2026-12-31` ≡ `2026-01-01~2026-12-31` |
| R8 | direction 中译英 | `增持` ≡ `increase` |

**适用范围由 `spec/v0.3/registry.mjs` 的 `unit` 驱动，不在本文件手抄一份**。这不是洁癖 —— 真实踩到的：契约里 `change_date` 的 unit是 `date_range`，字段名里没有 "range"，按名字猜会整条漏掉区间规则。

### 反例（判据的底线，由守卫双向断言）

| 反例 | 为什么必须判异 |
|---|---|
| `100万元` ≠ `100` | 「万」是真换算不是装饰，剥掉就是错值 |
| `2.5` ≠ `0.025` | 百分点 vs 分数，差 100 倍 |
| `张三` ≠ `李四` | 人名不同 |
| `null` ≠ `0` | 0 是值，null 是缺 |
| `1200000`(number) vs `"1200000"`(string) | 数值相同但 **JSON 类型不同** → 单列 `type_only`，计数上报、**不否决** |

★ 只测"格式差异判同"会得到永远 pass 的假判据；只测"语义差异判异"会得到永远 fail 的假判据。**必须双向测。**

## 五、验证过程中抓到的三个真 bug

### 1★ `statusOf` 优先级写反 —— 一次把 S1 判据整个废掉

最初写成 `status_override || status_raw || "extracted"`。而**魏信封 v0.3 的真实字段是 `status`**（6 态直接放这），`status_override` 根本不存在。

后果：所有 `not_mentioned` / `not_applicable` / `not_disclosed` 全被读成 `extracted`，于是 `A侧 not_mentioned vs B侧 not_disclosed` 这种**真状态词差异被判为"相同"** —— 表面看是 pass。

**这与 D10 同源：判据的默认值不能是"最宽松的那个"。** 读不到就该显式标记 `unknown_status`，而不是悄悄当成 `extracted`。现在的优先级：`status_override` → `status` → `status_raw` → `unknown_status`（不是 extracted）。

抓它的不是合成用例，是真实数据 —— `awd_002` 严格判报2 处差异而本判据报 0，这个"数对不上"就是信号。

### 2 ★ `change_date` 区间规则按字段名匹配失效

契约里该字段 unit 是 `date_range`，字段名里没有 range/period。改为**由注册表 `unit` 决定适用范围**。

### 3 ★ `parity()` 大小写索引崩溃 → 自检整体挂掉

`mismatch_detail` 里写成 `["S0",...].filter(L => !c[L].pass)`，但 case 对象键是**小写** `s0` ⇒ `c["S0"]` 是 `undefined` ⇒ TypeError ⇒ 整个 `parity()` 崩。

**崩掉的自检等于没有自检。** 顺带补了防御：`judged = ran.filter(c => c.s0 && c.s1 && c.s2 && c.s3)`，并新增 `cases_unjudged` 计数（跑"成功"但没产出可判结果的例数，不许混进通过）。

## 六、判据的可追溯要求

引用本判据的**任何结论**都必须同时给出四项（已写进 `CRITERIA_META.required_attribution`，并由 `engine_check` 断言）：

```
criteria_version + s2.value_diff + s2.format_only + cases_ran
```

`parity()` 返回体新增：`criteria_version`、`criteria_meta`（五级说明 / 归一化条数 / 注册表状态 / 不覆盖什么 / 引用要求）、`cases_unjudged`、`format_only_total`、`type_drift_total`、`mismatch_detail[].failed_levels`。

**不通过时必须指出卡在哪一级** —— 只给一个 `mismatch` 是没法归因的。

## 七、明写「这套判据不覆盖什么」

写在 `CRITERIA_META.not_covered_by_these`，每次出报告都随行，避免后来者误以为它万能：

1. 跨批召回缺口（事件数差异属 S0，但本页只判 Web/CLI 两侧）
2. 对 Gold 的正确性 —— **那是另一套判据**：按 `source.file_id` 配文件 + `evKey` 配事件，分母与结论含义都不同
3. 出处 quote 是否真能在 `block.text` 里定位 —— 走 `demo/_evidence_quote_real.js`
